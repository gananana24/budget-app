# プログラミング思想

更新日: 2026-09-26

この文書は、このリポジトリで設計・実装・レビューを行うときの判断基準を定める。機能要件は [MVP要件](./mvp-spec.md)、具体的な技術判断は [技術構成](./tech-stack.md)、テストの詳細は [テスト戦略](./testing-strategy.md) を正とする。

## 優先順位

判断が衝突した場合は、次の順に優先する。

1. データの正しさ、認可、秘密情報の保護
2. 合意済みの利用者価値と機能要件
3. 単純さと読みやすさ
4. 変更しやすさと検証しやすさ
5. 計測で必要性を確認した性能改善

思想と具体的な機能要件が衝突した場合は、どちらかを暗黙に優先しない。仕様と判断理由を確認し、合意した変更を実装・テスト・文書へ同時に反映する。

## YAGNIと抽象化

- YAGNIを守り、現在の要件にない機能、拡張ポイント、設定項目、抽象化を先回りして作らない。
- 将来の可能性だけを理由に、DIコンテナ、汎用Repository、プラグイン機構、共通基底クラスを追加しない。
- データ消失、認可漏れ、移行困難など、後から直す費用が極端に高い境界は現在の要件として先に設計する。
- 見た目が似ているだけのコードは共通化しない。同じ業務概念を表し、同じ理由で変更されると確認できたときに共通化する。
- 小さな重複は、誤った抽象化よりも許容する。

## バックエンドの基本構造

### 解決したい問題

業務ルールをHTTP、DB、認証サービス、実行環境から分離し、外部技術の変更やテストの都合で業務ロジックが歪まないようにする。

### 採用する構造

基本は次の4層と、ランタイム固有のComposition Rootで構成する。

```text
presentation ──> application ──> domain
infrastructure ─> application ──> domain

Composition Root
├── presentationを生成
├── infrastructureの実装を生成
└── applicationへ依存を注入
```

- `domain`: 業務ルール、値、状態遷移、純粋な計算を置く。フレームワークや外部サービスへ依存しない。
- `application`: ユースケースと、外部機能へ要求するPortを置く。処理の流れを調整するが、HTTPやSQLの詳細を持たない。
- `infrastructure`: DB、認証、外部サービスなどのAdapterを置き、applicationのPortを実装する。
- `presentation`: HTTPやUIなどの入力をapplicationの入力へ変換し、結果を外部向けの表現へ変換する。
- Composition Root: 具体的なAdapterとユースケースを生成し、依存を明示的に組み立てる。このリポジトリではCloudflare Workers固有の `src/backend/worker/` が担う。

### 採用する条件

- 業務判断と外部I/Oが同じ機能に存在する。
- DBや外部サービスを使わずに検証したい業務ルールがある。
- 層を分けることで依存方向と変更理由が明確になる。

### 採用しない形

- 単純な委譲のためだけにクラスやインターフェースを増やさない。
- 各テーブルへ機械的にRepositoryを一つずつ作らない。
- パターン名に合わせるためだけの空の層、基底クラス、ラッパーを作らない。
- `domain` や `application` からHono、Clerk、Neon、Cloudflare Workersを参照しない。

### 許容する例外

業務ルールを持たない小さな処理では、全層にファイルを作る必要はない。ただし、外部入力の検証、認可、秘密情報の保護は省略しない。

## Functional Core, Imperative Shell

- 計算と判断は、可能な限り入力から出力を返す純粋関数にする。
- DB、HTTP、現在時刻、乱数、ログなどの副作用は外側へ寄せる。
- ドメインロジックの内部で現在時刻を取得せず、判定基準となる日付や時刻を引数で受け取る。
- 副作用を隠すグローバル状態やSingletonを作らない。
- 純粋関数にするために処理全体の理解が難しくなる場合は、読みやすいまとまりを優先する。

## ドメインモデル

- 基本は純粋関数と明示的な型で業務ルールを表現する。
- データを包むだけのEntityクラスは作らない。
- 生成時から常に不変条件を保証する必要があり、その値が複数のユースケースで振る舞いを持つ場合にValue Objectを検討する。
- Value Object、Entity、集約などの用語を使うこと自体を目的にしない。

## PortとAdapter

### 解決したい問題

ユースケースがDBのテーブル構成や外部サービスのSDKへ直接依存することを防ぐ。

### 採用する形

- Portは、テーブル単位ではなく仕事単位で定義する。
- 初期化、月次取得、予算保存など、整合性を保つ処理単位を一つの操作として表す。
- 読み取りは、利用者の画面や集計に必要な形を直接返してよい。
- 複数テーブルの更新は、Adapter内部の一つのトランザクションにまとめる。

例えば初回利用時の処理は、複数の汎用Repositoryをapplicationから順番に呼ぶのではなく、`BootstrapStore.initializeUser()` のように一つの仕事として表す。

### 採用しない形

- `findAll`、`save`、`delete`を揃えただけの汎用Repositoryを作らない。
- 将来使うかもしれないメソッドをPortへ追加しない。
- SQL行やSDKのレスポンス型を、そのままdomainへ渡さない。

## エラー処理

- 入力不正や業務上起こり得る分岐は、`Result` など戻り値の型で明示する。
- ユースケース全体を中断し、外側で共通変換する失敗は、コードを持つapplicationエラーとして扱ってよい。
- DB障害や設定不備などの想定外エラーは握りつぶさず、presentationの境界で一般化したレスポンスへ変換する。
- 利用者向けの日本語文言はAPIで生成せず、フロントエンドの文言リソースで管理する。
- 例外メッセージ、接続文字列、トークン、個人情報をレスポンスや通常ログへ出さない。

## 状態の表現

- 意味の異なる状態を、同じ値や曖昧な真偽値へ押し込めない。
- 予算未設定と0円予算のように振る舞いが異なる状態は、データと型で区別する。
- 複数の状態を表す必要がある場合は、真偽値の組み合わせより判別可能な型を優先する。
- `null` は「値が存在しない」という意味が明確な場合に使う。

## TypeScript

- HTTP入力、環境変数、DB結果、外部サービス応答は信頼せず、実行時に検証する。
- 層をまたぐPortとユースケースの入出力は明示的に型付けする。
- 関数内部の自明な型は推論へ任せる。
- `any` と `as unknown as T` で型エラーを隠さない。
- コンパイル時の型と、実行時に外部入力が正しいことを区別する。

## データ整合性

- 利用者へ早く適切なエラーを返すため、画面とAPIで入力を検証する。
- データの最終的な整合性は、外部キー、一意制約、`CHECK`制約でも保証する。
- 複数操作を一体として成功させる必要がある場合は、DBトランザクションを使う。
- ネットワーク越しの処理は再送され得る前提にし、重複が問題になる操作は冪等にする。
- 同時実行対策は、実際に競合し得る整合性境界へ限定する。
- 業務処理を無制限にDBトリガーへ移さない。DB制約で自然に表現できない処理はアプリケーションコードに置く。

## セキュリティと認可

- ブラウザのコード、状態、リクエスト内容は利用者が自由に改変できる前提にする。
- フロントエンドの非表示、`disabled`、ルーティング制御は操作性のために使い、認可として扱わない。
- 認証済みであることと、対象データを操作する権限があることを分けて確認する。
- 利用者IDや家計IDをクライアントから信用せず、認証情報からサーバー側で解決する。
- 読み取り、作成、更新、削除のすべてで、対象データが認証済み利用者の家計に属することをサーバー側で確認する。
- 他人のIDと存在しないIDは同じ404として扱い、データの存在を推測させない。
- 別利用者のIDへ差し替えたリクエストを拒否する結合テストを、各操作の必須条件とする。

## API設計

- APIはユースケースに必要な契約として設計し、DBテーブルをそのまま公開しない。
- 成功、失敗、未設定などの意味を入出力で明示する。
- 一つの画面に必要な複数テーブルのデータは、必要に応じて一つの読み取り契約へまとめる。
- 用途の異なる更新を万能な汎用APIへまとめない。

## フロントエンド

- 状態は必要な場所の近くに置く。
- 入力途中の値や画面内の選択はローカルstateから始める。
- 複数画面で複雑な同期が必要になるまで、グローバル状態管理ライブラリを追加しない。
- コンポーネントは、独立した責務、再利用されるUI規則、固有の状態や操作を持つ単位で分割する。
- 数行の表示を隠すだけのコンポーネント分割は行わない。
- 見栄えより、迷わず操作でき、情報を正しく理解できることを優先する。
- HTMLの意味、キーボード操作、読み上げ、十分なタップ領域、色以外の状態表現を実装条件に含める。
- 画面側の入力検証をサーバー側検証の代わりにしない。

## フロントエンドとバックエンドの共有

- 同じ意味を持ち、同じ理由で変更される純粋なルールだけを共有する。
- 画面の入力途中の状態と、APIの確定済み入力を一つの巨大な共通型へまとめない。
- 共有によって各境界の意味が曖昧になる場合は、重複を許容する。

## 依存ライブラリ

- 標準APIと既存依存で明確に実装できるなら、新しい依存を追加しない。
- 自作時の誤りや複雑さが、導入・更新・学習・セキュリティの負担を上回る場合に追加する。
- 保守状況、対象ランタイムとの互換性、実行サイズ、性能、ベンダー固定、機能過剰を確認する。

## 性能

- 正しさと読みやすさを優先し、推測だけで最適化しない。
- 計測結果、明確な規模要件、既知の高コスト処理がある場合に最適化する。
- N+1クエリ、無制限取得、明らかな不要I/Oなど、構造的な問題は最初から避ける。
- 複雑な最適化には、計測した問題と採用理由を設計文書へ残す。

## コードの伝達責任

- コードにはHowを表現する。名前と構造から、どのように実現しているかを読めるようにする。
- テストコードにはWhatを表現する。何が成立すべきかを、観察可能な振る舞いとして示す。
- コミットログにはWhyを残す。なぜ変更が必要で、何を解決したかを記録する。
- コードコメントにはWhy notを残す。一見自然な別案を採用しない理由を記録する。
- 処理内容を日本語へ言い換えるコメントや、コードから明らかな採用理由は書かない。
- 長期的に必要なWhyは、コミットログだけに閉じず設計文書へ残す。
- テストのAAAコメントは、構造を統一するための明示的な例外とする。

## 命名と分割

- 名前は実装手段ではなく、業務上の意味と責務を表す。
- `utils` や `helpers` に無関係な処理を集めない。
- 関数やファイルへ一律の行数制限を設けない。
- 入力検証、業務判断、SQL、HTTP変換など、変更理由や抽象度が混ざったら分ける。
- 分割によって処理の理解に必要な行き来が増えるだけなら、読みやすいまとまりを保つ。

## 変更管理

- 一つのIssueとPull Requestでは、一つの目的だけを完了させる。
- 目的に必要な実装、テスト、仕様更新は同じPull Requestへ含める。
- 後続Issueの機能を先回りして混ぜない。
- 周辺の問題は、現在の変更を安全に完成させるために必要な範囲だけ直す。独立した改善は別Issueにする。
- コミットはレビュー可能な論理単位にし、メッセージへWhyを残す。
- DBスキーマ変更はマイグレーションとしてコード管理し、共有環境へ適用済みのファイルは書き換えない。
- マイグレーションをアプリケーション起動時やリクエスト処理中に実行しない。

## ログと監視

- 障害を再現・切り分けるための事実を構造化して残す。
- リクエストID、処理名、HTTPメソッド、パス、結果、エラー種別、処理時間を必要な範囲で記録する。
- 認証トークン、接続文字列、支出メモ、個人情報、例外メッセージ全文を通常ログへ出さない。
- ログを業務データの履歴や監査証跡の代わりにしない。
