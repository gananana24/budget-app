# プログラミング思想

更新日: 2026-10-04

この文書は、このリポジトリで設計・実装・レビューを行うときの判断基準を定める。機能要件は [MVP要件](./mvp-spec.md)、バックエンドの構造は [バックエンド設計](./backend-architecture.md)、具体的な技術判断は [技術構成](./tech-stack.md)、テストの詳細は [テスト戦略](./testing-strategy.md) を正とする。

## 優先順位

判断が衝突した場合は、次の順に優先する。

1. データの正しさ、認可、秘密情報の保護
2. 合意済みの利用者価値と機能要件
3. 単純さと読みやすさ
4. 変更しやすさと検証しやすさ
5. 計測で必要性を確認した性能改善

思想と具体的な機能要件が衝突した場合は、どちらかを暗黙に優先しない。仕様と判断理由を確認し、合意した変更を実装・テスト・文書へ同時に反映する。

## YAGNIと抽象化

- YAGNIを守り、現在の要件にない機能、拡張ポイント、設定項目、抽象化を先回りして作らない。
- 将来の可能性だけを理由に、業務要件のないRepository method、プラグイン機構、共通基底クラスを追加しない。
- データ消失、認可漏れ、移行困難など、後から直す費用が極端に高い境界は現在の要件として先に設計する。
- 見た目が似ているだけのコードは共通化しない。同じ業務概念を表し、同じ理由で変更されると確認できたときに共通化する。
- 小さな重複は、誤った抽象化よりも許容する。

## バックエンドの基本構造

### 解決したい問題

業務ルールをHTTP、DB、認証サービス、実行環境から分離し、外部技術の変更やテストの都合で業務ロジックが歪まないようにする。

### 採用する構造

基本はdddpyを基準とする次の4層と、Cloudflare Workersのエントリーポイントで構成する。詳細は [バックエンド設計](./backend-architecture.md) を正とする。

```text
presentation ───────────────> usecase ──> domain
presentation ─> infrastructure/di ─────> usecase
infrastructure/postgres ───────────────> domain
infrastructure/di ─> infrastructure/postgres
worker ─────────────> presentation / infrastructure/di
```

- `domain`: Entity、Value Object、Repository、Domain Exceptionを置く。フレームワークや外部サービスへ依存しない。
- `usecase`: 一つのpublic `execute`を持つユースケースを置き、Domain modelとRepositoryを使って処理を調整する。
- `infrastructure`: PostgreSQLなどのRepository実装、DB行の型とmapper、依存関係とライフサイクルの組み立てを置く。
- `presentation`: HTTP入力をDomainが受け取る値へ変換し、UseCaseの結果と例外をHTTP向けのschemaへ変換する。
- `worker`: Cloudflare Workersのエントリーポイントとし、ランタイムをHonoとInfrastructureへ接続する。

- `domain`と`usecase`からHono、Clerk、PostgreSQL、Cloudflare Workersを参照しない。
- RepositoryはテーブルではなくEntityまたは集約の境界に対応させる。
- UseCase、Repository、Entity、Value Objectの責務を別層へ混在させない。
- 未実装機能の空ディレクトリや未使用methodは先に作らない。

## Domain logic and side effects

- 業務判断はEntityとValue Objectへ置き、UseCaseがRepositoryを介して副作用を調整する。
- DB、HTTP、現在時刻、乱数、ログなどの外部要因をDomain modelへ直接持ち込まない。
- Domain modelの内部で現在時刻を取得せず、判定基準となる日付や時刻をValue Objectまたは引数で受け取る。
- 副作用を隠すグローバル状態やSingletonを作らない。
- 値の変換や集計に識別子と状態遷移が不要な場合は、Domain内の純粋関数を使用してよい。

## ドメインモデル

- 識別子を持ち、状態と振る舞いを持つ業務概念はEntityとして実装する。
- 識別子、金額、日付、対象月、名前など、値自体に不変条件または振る舞いがある概念はValue Objectとして実装する。
- Entityは識別子で同一性を判断し、業務上の操作と`equals()`などの明示的な比較methodを公開する。
- Value Objectは生成時から不変条件を保証し、生成後は変更できないようにする。不変条件や振る舞いがない内部データは`type`で表す。
- DB行やHTTP payloadをDomain modelとして直接利用せず、境界でEntityとValue Objectへ変換する。

## Repository

### 解決したい問題

UseCaseがDBのテーブル構成や外部サービスのSDKへ直接依存することを防ぐ。

### 採用する形

- Repositoryの抽象は`domain/<feature>/repositories/`へ置く。
- RepositoryはEntityまたは集約単位で定義し、必要な`save`、`findById`、`findAll`、`delete`などを公開する。
- Repository実装は`infrastructure/<technology>/<feature>/`へ置き、DB行の型とmapperでDomain modelへ変換する。
- 複数Repositoryを使うUseCaseの接続とトランザクションは`infrastructure/di`で同じライフサイクルへ束縛する。
- 読み取りでもDB行をそのまま返さず、Domain modelまたは明示的なUseCase出力へ変換する。

### 採用しない形

- 将来使うかもしれないメソッドをRepositoryへ追加しない。
- すべてのEntityへ共通する汎用Repository基底クラスを作らない。
- SQL行、`pg`の型、SDKのレスポンス型をDomainとUseCaseへ渡さない。

## エラー処理

- 入力不正、不正な状態遷移、権限不足、対象なしなど、呼び出し側が判断・回復する業務上の失敗は、機能ごとのDomain Exceptionで明示する。
- 業務上の失敗を、理由の分からない `false` や `null` に押し込めない。
- プログラミングエラーや、成立してはならない状態は例外として扱う。
- PresentationはDomain ExceptionをHTTP statusと安定したエラーコードへ変換する。
- DB障害や設定不備などの想定外エラーは握りつぶさず、presentationの境界で一般化したレスポンスへ変換する。
- `catch` は、その場で回復する、別の意味へ翻訳する、または処理境界で記録する場合に限定する。
- 空の `catch` や、ログを出して同じエラーを投げ直すだけの処理は作らない。情報を付加して投げ直す場合は `cause` で元のエラーを保持する。
- 利用者向けの日本語文言はAPIで生成せず、フロントエンドの文言リソースで管理する。
- 例外メッセージ、接続文字列、トークン、個人情報をレスポンスや通常ログへ出さない。

## 状態の表現

- 意味の異なる状態を、同じ値や曖昧な真偽値へ押し込めない。
- 予算未設定と0円予算のように振る舞いが異なる状態は、データと型で区別する。
- 複数の状態を表す必要がある場合は、真偽値の組み合わせより判別可能な型を優先する。
- `null` は「値が存在しない」という意味が明確な場合に使う。

## TypeScript

### 型と外部入力

- HTTP入力、環境変数、DB結果、外部サービス応答は信頼せず、実行時に検証する。
- 層をまたぐRepositoryとUseCaseの入出力は明示的に型付けする。
- 関数内部の自明な型は推論へ任せる。
- コンパイル時の型と、実行時に外部入力が正しいことを区別する。
- 型が分からない外部入力には `unknown` を使い、検証または型の絞り込みを終えるまで利用しない。
- `any` はアプリケーションコードでは原則使わない。型定義のないライブラリなどで避けられない場合は、小さな境界内に閉じ込め、具体的な型へ変換してから返す。
- `as` は安全性を加える機能ではなく、型検査を迂回する操作として扱う。外部入力を型アサーションだけで信用しない。
- `as unknown as T` は原則禁止する。避けられない型アサーションは境界へ閉じ込め、他の方法を採らなかった理由をコメントに残す。
- リテラルの型を保つ `as const` と、推論を維持したまま適合を検査する `satisfies` は目的に沿って使う。
- Union、タプル、関数型、型の変換には `type` を使う。宣言の拡張性や外部契約として開かれていることに意味がある場合は `interface` を使う。
- アプリケーション内部の閉じたオブジェクト型は、意図しない宣言マージを避けるため `type` を基本にする。

### 変数と変更

- 再代入しない変数には `const` を使い、`var` は使わない。`const` 自体を目的にせず、再代入が状態遷移や反復を最も明確に表す場合は `let` を使う。
- `const` は変数への再代入を防ぐだけで、オブジェクト自体を不変にするものではないことを区別する。
- 関数へ渡されたオブジェクトや配列を変更せず、新しい値を返すことを基本にする。
- 関数内だけで完結する一時的な配列やオブジェクトは、可読性や性能に適するなら局所的に変更してよい。変更可能な値を外へ漏らさない。
- 関数が入力を変更しない契約に意味がある場合は、`readonly`、`ReadonlyArray<T>`、readonlyプロパティで型にも表す。特にドメイン値と公開境界で優先する。
- 新しい値を組み立てる内部実装まで機械的に不変化しない。

### 値と状態

- `undefined` は未指定、未提供、プロパティ不在を表し、`null` は明示的に値がないことを表す。
- 同じ欠如を `null` と `undefined` の両方で無秩序に流さず、APIやDBとの境界でドメイン上の表現へ正規化する。
- `0`、空文字、`false` が有効な値になり得る場合はtruthy/falsy判定に頼らず、`null`、`undefined`、または具体的な値と比較する。
- 等値比較には厳密等価演算子を使う。`value == null` で二種類の欠如をまとめず、境界で正規化する。
- Optional chainingとnull合体演算子は、値が存在しないことが仕様上正しい場合に使う。必須データへ `?.` を連鎖させて不整合を隠さない。
- 非nullアサーション `!` は原則避け、分岐や実行時検証で型を絞り込む。TypeScriptが表現できない保証が別の場所に存在する場合だけ、理由を説明できる範囲で使う。
- TypeScript内部で閉じた固定値には、文字列リテラルのUnionや `as const` を基本にする。
- 状態ごとに保持するデータが異なる場合は判別可能なUnionを使い、不正な状態を表現しにくくする。
- `enum` は外部仕様との対応や実行時オブジェクトとして必要な場合に使い、慣習だけでは採用しない。

### 関数

- モジュールやスコープの主要な名前付き関数にはfunction宣言を使う。コールバック、クロージャ、関数を値として渡す場面にはアロー関数を使う。
- 外側の `this` を引き継ぐ必要がある場合はアロー関数を使う。呼び出し方で変わる `this` は原則避け、必要ならメソッドまたはfunctionを使う。
- オーバーロードとジェネレーターにはfunctionを使う。明示的な関数型への代入に意味がある場合は `const` とアロー関数を使ってよい。
- すべてをアロー関数またはfunctionへ統一せず、構文の意味で選ぶ。
- 単純な値変換のアロー関数は式をそのまま返す形にし、複数手順、分岐、副作用を含む場合は波括弧を使う。副作用目的のコールバックから意図せず値を返さない。
- 前提を満たさない入力や対象外の処理はearly returnで終了し、不要な `else` と深いネストを避ける。対称な二分岐は、読みやすければ `if` / `else` を使う。
- 三項演算子は単純な二者択一に使う。ネストした三項演算子と、副作用を含む三項演算子は使わない。複数状態は `switch` や判別可能なUnionで扱う。

### 引数と分割代入

- 少数で意味が明確な値には位置引数を使う。同じ型の引数が並ぶ、項目が多い、または任意項目がある場合はオブジェクト引数を使う。
- 呼び出し側で意味が分からない真偽値引数を避け、名前付きの選択肢や目的別の関数で意図を表す。
- 引数が一つしかない処理まで機械的にオブジェクト化しない。
- 分割代入は、処理が依存する値を明示できる場合に使う。小さく浅い構造では使えるが、ドメイン上のまとまり、値の出所、検証の境界を壊す場合は元のオブジェクトを保つ。
- `unknown` などの外部入力は、検証して内部表現へ変換してから分割代入する。
- 深い分割、過剰な別名、restの併用は、元の構造を復元しにくくするなら避ける。名前の衝突解消や外部表現から内部表現への変換など、別名に意味がある場合は使う。
- 分割代入のデフォルト値は `undefined` にだけ適用されることを踏まえ、未指定時の仕様がその場所に属する場合に使う。

### コレクションと非同期処理

- 単純な変換、抽出、検索、集約には、意図と性能特性に合う `map`、`filter`、`find`、`some`、`reduce` などを使う。
- `reduce` を特別に避けない。単一走査で集約する処理には自然な選択肢とし、処理を詰め込みすぎて意図が読めなくなる使い方は避ける。
- 途中終了、複数の状態更新、非同期処理など、ループの方が読みやすい場合は `for...of` を使う。
- 独立した非同期処理は、順序や負荷制限に問題がなければ `Promise.all` などで並行実行する。依存関係がある処理だけを順番に `await` する。
- `forEach(async () => ...)` と未処理のPromiseを作らない。逐次処理には `for...of`、並行処理にはPromiseの配列を使う。
- `await` は、エラー処理や処理順をその場所で明確にする必要がある場合に使う。

### クラス

- EntityとValue Objectは、不変条件、状態、振る舞いを閉じ込める必要がある場合にclassで表す。
- RepositoryとUseCaseの契約は`interface`で表し、具象実装をclassで表す。共有状態や共通実装が必要な場合だけ`abstract class`を使う。
- DB行はInfrastructure固有の`type`で表し、mapper関数でDomain modelへ変換する。
- 状態を持たない局所的な計算と変換には関数を使ってよい。
- クラスを使う場合も継承より合成を優先し、関数をまとめるだけの静的クラスは作らない。

### importとexport

- 型だけの依存は `import type` で明示する。同じモジュールから値と型の両方を読む場合は、一つのimport文へまとめてよい。
- 名前付きexportを基本とする。default exportは、フレームワークが要求する場合や、モジュールの主役が一つであることに意味がある場合に使う。
- 多数のファイルから再exportするだけで依存関係や循環参照を見えにくくする、巨大なbarrel exportは作らない。基本は定義元から直接importする。
- 設計上のモジュールが公開する契約を限定する入口としての `index.ts` は使ってよい。モジュール外から内部実装を直接importさせない境界として扱う。

### フォーマットと静的解析

- インデント、引用符、セミコロン、import順など、意味を持たない表記はBiomeなどの自動化へ任せ、レビューで議論しない。
- Lintルールは、実際の不具合防止や設計意図に根拠があるものを採用し、好みだけのルールを増やさない。
- 無効化コメントを散らす前に、コードまたは設定を見直す。例外が必要なら、影響範囲と理由を明確にする。

## データ整合性

- 利用者へ早く適切なエラーを返すため、画面とAPIで入力を検証する。
- データの最終的な整合性は、外部キー、一意制約、`CHECK`制約でも保証する。
- 複数操作を一体として成功させる必要がある場合は、DBトランザクションを使う。
- ネットワーク越しの処理は再送され得る前提にし、重複が問題になる操作は冪等にする。
- 同時実行対策は、実際に競合し得る整合性境界へ限定する。
- 業務処理を無制限にDBトリガーへ移さない。DB制約で自然に表現できない処理はアプリケーションコードに置く。

## セキュリティと認可

- ブラウザのコード、状態、リクエスト内容は利用者が自由に改変できる前提にする。
- フロントエンドの非表示、`disabled`、ルーティング制御は操作性のために使い、認可として扱わない。
- 認証済みであることと、対象データを操作する権限があることを分けて確認する。
- 利用者IDや家計IDをクライアントから信用せず、認証情報からサーバー側で解決する。
- 読み取り、作成、更新、削除のすべてで、対象データが認証済み利用者の家計に属することをサーバー側で確認する。
- 他人のIDと存在しないIDは同じ404として扱い、データの存在を推測させない。
- 別利用者のIDへ差し替えたリクエストを拒否する結合テストを、各操作の必須条件とする。

## API設計

- APIはユースケースに必要な契約として設計し、DBテーブルをそのまま公開しない。
- 成功、失敗、未設定などの意味を入出力で明示する。
- 一つの画面に必要な複数テーブルのデータは、必要に応じて一つの読み取り契約へまとめる。
- 用途の異なる更新を万能な汎用APIへまとめない。

## フロントエンド

- 状態は必要な場所の近くに置く。
- 入力途中の値や画面内の選択はローカルstateから始める。
- 複数画面で複雑な同期が必要になるまで、グローバル状態管理ライブラリを追加しない。
- コンポーネントは、独立した責務、再利用されるUI規則、固有の状態や操作を持つ単位で分割する。
- 数行の表示を隠すだけのコンポーネント分割は行わない。
- 見栄えより、迷わず操作でき、情報を正しく理解できることを優先する。
- HTMLの意味、キーボード操作、読み上げ、十分なタップ領域、色以外の状態表現を実装条件に含める。
- 画面側の入力検証をサーバー側検証の代わりにしない。

## フロントエンドとバックエンドの共有

- 同じ意味を持ち、同じ理由で変更される純粋なルールだけを共有する。
- 画面の入力途中の状態と、APIの確定済み入力を一つの巨大な共通型へまとめない。
- 共有によって各境界の意味が曖昧になる場合は、重複を許容する。

## 依存ライブラリ

- 標準APIと既存依存で明確に実装できるなら、新しい依存を追加しない。
- 自作時の誤りや複雑さが、導入・更新・学習・セキュリティの負担を上回る場合に追加する。
- 保守状況、対象ランタイムとの互換性、実行サイズ、性能、ベンダー固定、機能過剰を確認する。

## 性能

- 要件を満たす実装の中から、最も単純で意図が明確なものを選ぶ。「常に可読性」や「常に最速」のように一方を絶対視しない。
- 計測結果、明確な規模要件、既知の高コスト処理がある場合に最適化し、将来速くなるかもしれないという理由だけで複雑さを増やさない。
- N+1クエリ、無制限取得、過剰なデータ取得、明らかな不要I/Oや多重走査など、構造から問題が分かるものは最初から避ける。
- 複雑な最適化には、計測した問題と採用理由を設計文書へ残す。

## コードの伝達責任

- コードにはHowを表現する。名前と構造から、どのように実現しているかを読めるようにする。
- テストコードにはWhatを表現する。何が成立すべきかを、観察可能な振る舞いとして示す。
- コミットログにはWhyを残す。なぜ変更が必要で、何を解決したかを記録する。
- コードコメントにはWhy notを残す。一見自然な別案を採用しない理由を記録する。
- 処理内容を日本語へ言い換えるコメントや、コードから明らかな採用理由は書かない。
- 長期的に必要なWhyは、コミットログだけに閉じず設計文書へ残す。
- テストのAAAコメントは、構造を統一するための明示的な例外とする。

## 命名、定数、分割

- 名前は実装手段ではなく、業務上の意味と責務を表す。
- 真偽値には `is`、`has`、`can`、`should` などを使い、時間、金額、件数など単位が曖昧になる値は名前に単位を含める。
- `data`、`info`、`item`、`manager` などの広すぎる名前は、文脈だけで意味が明白な局所変数を除いて避ける。
- 業務ルール、単位、制限値、複数箇所で共有する値には、その意味が伝わる定数名を付ける。0件との比較など、自明な値まで機械的に定数化しない。
- 定数や処理は、重複しているという理由だけで共有せず、同じ意味を持ち、同じ理由で変更される場合に共有する。
- ファイルはコードの配置と読みやすさを基準に分ける。設計上のモジュールは、業務上の責任、変更理由、公開する契約を基準に分け、複数ファイルを含んでよい。
- 一緒に変更される型、関数、小さな補助処理は近くに置き、再利用されるかもしれないという理由だけで共通化しない。
- `utils.ts` や `helpers.ts` に無関係な処理を集めず、役割が分かる名前を付ける。
- 関数やファイルへ一律の行数制限を設けない。
- 一関数一ファイルを機械的な規則にしない。
- 入力検証、業務判断、SQL、HTTP変換など、変更理由や抽象度が混ざったら分ける。
- 分割によって処理の理解に必要な行き来が増えるだけなら、読みやすいまとまりを保つ。

## 変更管理

- 一つのIssueとPull Requestでは、一つの目的だけを完了させる。
- 目的に必要な実装、テスト、仕様更新は同じPull Requestへ含める。
- 後続Issueの機能を先回りして混ぜない。
- 周辺の問題は、現在の変更を安全に完成させるために必要な範囲だけ直す。独立した改善は別Issueにする。
- コミットはレビュー可能な論理単位にし、メッセージへWhyを残す。
- DBスキーマ変更はマイグレーションとしてコード管理し、共有環境へ適用済みのファイルは書き換えない。
- マイグレーションをアプリケーション起動時やリクエスト処理中に実行しない。

## ログと監視

- 障害を再現・切り分けるための事実を構造化して残す。
- リクエストID、処理名、HTTPメソッド、パス、結果、エラー種別、処理時間を必要な範囲で記録する。
- 認証トークン、接続文字列、支出メモ、個人情報、例外メッセージ全文を通常ログへ出さない。
- ログを業務データの履歴や監査証跡の代わりにしない。
