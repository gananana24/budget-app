# 家計簿アプリ MVP開発計画

更新日: 2026-09-23

機能要件は [MVP要件](./mvp-spec.md)、採用技術と設計判断は [技術構成](./tech-stack.md) を正とする。この文書は、MVPを実装して公開するまでの順序と、GitHub Issueで管理する実装単位を定める。

## 開発方針

- スマートフォンで実際に使える流れを早く通し、最初の実用到達点を「Googleでログインし、支出を登録して当月一覧で確認できる」とする。
- API、DB、画面を機能単位でつなぐ。共通基盤だけを長期間作り続けない。
- アプリケーションの品質確認はpnpm、Issue・ブランチ・Pull Request・CI/CDなどリポジトリ運用はTaskfileへ入口を分ける。
- `domain`と`application`を外部サービスから分離するが、MVPで使わない抽象化、DIコンテナ、汎用Repositoryは作らない。
- DB変更はSQLマイグレーションを先に追加し、生SQLと制約を同じIssueで検証する。
- 認可はすべてサーバー側で判定し、クライアントから家計IDを受け取らない。
- 自動テストは、金額計算、日付、認可、DB制約、予算継承など、誤るとデータや利用者分離を壊す箇所に絞る。
- CSV書き出しはMVPの最後に実装する。

## 到達点

### 最初の実用到達点

- Googleログイン後に初期設定が自動で完了する。
- 当月に支出を手入力できる。
- 登録した支出と合計を当月画面で確認できる。
- 別利用者の家計データを読み書きできないことをテストで確認できる。

### MVP完了条件

- [MVP要件](./mvp-spec.md) のMVP範囲がスマートフォン画面で利用できる。
- iPhoneとAndroid相当の画面幅で、ログイン、月次確認、支出管理、費目管理、予算管理、CSV書き出しを完了できる。
- 未来日付、未来月、不正な金額、別家計のIDをAPIが拒否する。
- DBマイグレーション、型検査、Lint、主要テスト、プロダクションビルドが成功する。
- Cloudflare Workersへ公開し、ClerkとNeonの本番設定で主要操作を確認できる。
- READMEにローカル開発、マイグレーション、環境変数、デプロイ手順が記載されている。

### T01 開発基盤と品質チェックを整える

**依存:** なし

**実装内容:**

- パッケージマネージャーをpnpmに統一し、テンプレート由来の名前・README・不要ファイルを整理する。
- `dev`、`build`、`lint`、`typecheck`、`test`、`check`のスクリプトを整える。
- Vitestと、必要最小限のテスト用設定を追加する。
- `.env.example`に変数名と用途だけを記載し、秘密値は含めない。

**受け入れ条件:**

- 新しい開発者がREADMEの手順で起動できる。
- 一つのコマンドで型検査、Lint、テスト、ビルドを実行できる。
- npmとpnpmのロックファイルが混在していない。

### T02 PostgreSQLスキーマとマイグレーションを作る

**依存:** T01

**実装内容:**

- dbmateを導入し、ローカル用とNeon用の実行手順を用意する。
- `users`、`households`、`household_members`、`categories`、`expenses`、`budget_periods`、`monthly_budgets`を作成する。
- 仕様書どおりの外部キー、複合キー、CHECK制約、一意制約、インデックスを追加する。
- マイグレーションの適用と、空のDBからの再構築を検証する。

**受け入れ条件:**

- 空のPostgreSQLへマイグレーションを適用できる。
- 費目の家計内重複、別家計の費目を参照する支出、不正な金額、月初以外の予算月をDBが拒否する。
- マイグレーションをWorkerのリクエスト処理から実行していない。

### T03 バックエンドの基本構造と共通処理を作る

**依存:** T01

**実装内容:**

- `domain`、`application`、`infrastructure`、`presentation/http`、`worker`の基本構造を作る。
- Neon HTTP接続、環境変数の型、依存関係の組み立てを実装する。
- APIの入力検証、共通エラー形式、404変換、予期しないエラーの処理を用意する。
- 日付、月、金額、メモ、費目名に使う検証処理を配置する。

**受け入れ条件:**

- `domain`と`application`がHono、Clerk、Neon、Workersへ依存していない。
- APIエラーが仕様書の共通形式で返る。
- 秘密値をログやレスポンスへ出さない。

### T04 ClerkのGoogleログインとAPI認証を実装する

**依存:** T03

**実装内容:**

- ClerkをReactとHonoへ組み込み、Googleログインだけを提供する。
- 未認証画面、ログイン処理、ログアウト処理、セッション復元を実装する。
- APIでClerk利用者IDを検証し、認証情報をユースケースへ渡す。
- 未認証リクエストを拒否する共通ミドルウェアを追加する。

**受け入れ条件:**

- Googleアカウントでログイン・ログアウトできる。
- 未認証利用者はアプリ本体と保護APIを利用できない。
- クライアントが送った利用者IDを認証情報として信用していない。

### T05 利用開始時の初期化を実装する

**依存:** T02、T04

**実装内容:**

- `POST /api/bootstrap`を実装する。
- 利用者、個人用家計、所属、初期費目9件、今月の予算期間を一つの整合した処理で作る。
- 再送や同時実行で重複しない生SQLを実装する。
- Clerk利用者IDから利用者と所属家計を解決する認可コンテキストを作る。

**受け入れ条件:**

- 初回ログインで必要なデータが一度だけ作られる。
- 同じ利用者が複数回呼んでも同じ家計を利用する。
- 別利用者には別の個人用家計と初期費目が作られる。

### T06 モバイル画面の土台と日本語文言管理を作る

**依存:** T01、T04

**実装内容:**

- スマートフォン向けのアプリシェル、画面遷移、読み込み、空状態、エラー表示を作る。
- 日本語文言を多言語対応の仕組みに集約し、コンポーネントへ直書きしない構造にする。
- APIクライアントとAPIエラーコードから表示文言への変換を用意する。
- 金額、日付、月を日本語・日本時間で表示する共通処理を作る。

**受け入れ条件:**

- 主要画面へスマートフォン幅で移動できる。
- 利用者向け文言とAPIエラー文言が日本語リソースから取得される。
- 通信中、データなし、通信失敗を区別して表示できる。

### T07 月次データ取得と集計を実装する

**依存:** T05

**実装内容:**

- `GET /api/months/:month`を実装する。
- 月内の支出、費目、予算、月全体と費目別の集計を生SQLで取得する。
- 未分類、予算未設定、0円予算を区別する。
- 過去月の閲覧では予算期間を作らず、未来月を拒否する。

**受け入れ条件:**

- 指定月の支出が日付・作成時刻・IDの降順で返る。
- 月全体の予算、全支出、残額と費目別集計が仕様どおりになる。
- 別家計のデータ、未来月、形式不正な月を取得できない。

### T08 支出の登録と当月一覧を縦に実装する

**依存:** T06、T07

**実装内容:**

- `POST /api/expenses`を実装する。
- 日付、金額、任意の費目、任意のメモを入力する画面を作る。
- 当月画面に支出一覧と支出合計を表示し、登録後に反映する。
- 未分類での登録、入力値の整形、未来日付の拒否を実装する。

**受け入れ条件:**

- ログインから支出登録、当月一覧での確認までスマートフォン画面で完了できる。
- 費目を選ばず登録でき、未分類と表示される。
- 不正な日付・金額・メモ・別家計の費目を画面とAPIで拒否する。

### T09 支出の編集・削除・絞り込みを実装する

**依存:** T08

**実装内容:**

- `PATCH /api/expenses/:expenseId`と`DELETE /api/expenses/:expenseId`を実装する。
- 過去月を含む支出の編集、削除確認、物理削除を画面へ追加する。
- 費目と未分類による月内一覧の絞り込みをブラウザ側で実装する。
- 非表示費目を維持した編集と、表示中費目への変更を扱う。

**受け入れ条件:**

- 自分の支出を編集・削除でき、集計へ即時反映される。
- 別家計の支出IDは存在しないIDと同じ404になる。
- 削除前に対象を確認でき、キャンセルできる。

### T10 月次ホームと月切り替えを完成させる

**依存:** T07、T09

**実装内容:**

- ログイン後のホームに予算、支出、残額、費目別状況を表示する。
- 今月と過去月を切り替える操作を実装し、未来月へ移動できないようにする。
- 予算超過、予算未設定、未分類支出を判別できる表示にする。
- グラフを使わず、金額と状態を読み取りやすく配置する。

**受け入れ条件:**

- 今月と任意の過去月の状況を確認できる。
- 未初期化の過去月を閲覧してもDBへ予算データが作られない。
- 予算超過と予算未設定をスマートフォン画面で区別できる。

### T11 費目管理を実装する

**依存:** T05、T06、T07

**実装内容:**

- 費目一覧、追加、名前変更、非表示、再表示のAPIと画面を実装する。
- 費目名の整形、家計内での大文字小文字を無視した重複拒否を実装する。
- 非表示・再表示時に現在月だけを必要に応じて初期化し、家計行ロックを使う。
- 初期費目と追加費目の表示順を維持する。

**受け入れ条件:**

- 費目を追加・改名・非表示・再表示できる。
- 非表示費目は新規支出の候補から消え、過去の支出表示には残る。
- すべての費目を非表示にしても未分類の支出を登録できる。

### T12 月別予算のDB処理とAPIを実装する

**依存:** T02、T05、T11

**実装内容:**

- `GET /api/months/:month/budget-draft`、`PUT /api/months/:month/budgets`、`DELETE /api/months/:month/budgets/:categoryId`を実装する。
- 対象月だけを初期化し、直前ではなく最も新しい過去の初期化済み月から予算を引き継ぐ。
- 家計行ロック、3秒のロックタイムアウト、冪等な初期化、非対話型トランザクションを実装する。
- 未設定と0円、非表示費目、過去月編集、後続月を変更しない規則をテストする。

**受け入れ条件:**

- 間の月を作らず、操作対象月だけを初期化できる。
- 同時実行や再送で既存予算を上書きしない。
- 過去月を変更しても既存の後続月は変わらない。
- ロック競合は再試行可能なエラーとして返る。

### T13 予算編集画面を実装する

**依存:** T10、T12

**実装内容:**

- 月単位で全費目の予算を編集する画面を作る。
- 未初期化月では引き継ぎ候補を下書きとして表示し、保存時だけ対象月へ確定する。
- 入力済みの費目だけをまとめて保存し、空欄だけの保存を拒否する。
- 費目ごとの「予算を削除」と確認画面を実装する。

**受け入れ条件:**

- 未設定、0円、正の予算額を区別して編集できる。
- 削除確認に対象月、費目名、現在額、「未設定に戻す」が表示される。
- API競合時に入力中の下書きが保持される。
- 保存後にホームの予算・残額・超過表示へ反映される。

### T14 PWA対応、公開設定、運用手順を整える

**依存:** T09、T10、T11、T13

**実装内容:**

- Web App Manifest、アイコン、ホーム画面追加、単独表示を実装する。
- iPhoneとAndroid相当の画面幅、Safe Area、タップ領域、入力操作を確認して修正する。
- Cloudflare Workers、Clerk、Neonの本番環境変数とデプロイ手順を整える。
- セキュリティヘッダー、ログ、エラー監視に必要な最小設定を追加する。
- READMEへ開発、DB、設定、デプロイ、障害確認の手順をまとめる。

**受け入れ条件:**

- iPhoneとAndroidでホーム画面から単独表示として起動できる。
- 本番環境でGoogleログインから予算管理まで主要操作を完了できる。
- 秘密値がリポジトリ、ブラウザ配信物、通常ログに含まれない。
- 新しい環境へREADMEの手順で再現できる。

### T15 CSV書き出しとMVP受け入れ確認を行う

**依存:** T14

**実装内容:**

- CSVの対象期間と列構成を確定し、要件書へ追記する。
- 自分の支出だけをCSVとして書き出すAPIと画面を実装する。
- 日本語、メモ内の改行・カンマ・引用符、未分類、日付、金額を正しく扱う。
- MVP要件を通した受け入れ確認を行い、未完了項目をIssue化する。

**受け入れ条件:**

- 指定した対象の支出を一般的な表計算ソフトで読めるCSVとして保存できる。
- 別家計のデータがCSVへ混ざらない。
- MVP完了条件を満たし、既知の制限がREADMEまたはIssueに記録されている。

## テスト方針

### ドメイン・アプリケーション

- 支出と予算の合計、残額、超過、未設定と0円の区別を単体テストする。
- 日本時間の今日、未来日付、対象月、入力上限を境界値でテストする。
- 予算初期化、引き継ぎ元の選択、非表示費目、後続月を変えない規則をテストする。

### DB・API

- マイグレーションを空のDBへ適用するテストを行う。
- DB制約と生SQLの主要な読み書きを実際のPostgreSQLでテストする。
- 別家計のIDを各更新・削除APIへ渡し、読み書きできないことを確認する。
- `POST /api/bootstrap`と予算初期化の再送・同時実行を確認する。

### 画面

- ログイン後の支出登録、編集、削除、費目管理、予算保存を主要な画面フローとして確認する。
- 小さなコンポーネントの実装をなぞるだけのテストは作らない。
- リリース前にiPhoneとAndroid相当のビューポートで主要フローを確認する。

## Issue管理

- GitHubのマイルストーン`MVP`へT01〜T15を登録する。
- Issueタイトルは`[Txx]`から始め、この文書との対応を保つ。
- 各Issueには依存タスク、実装内容、受け入れ条件、関連仕様へのリンクを記載する。
- 実装中に新しい作業が判明した場合、受け入れ条件の達成に必要なら同じIssueへ追加し、独立して検証・リリースできる作業なら別Issueにする。
- 仕様変更が必要になった場合は、実装だけを先行させず、`mvp-spec.md`または`tech-stack.md`を同じ変更で更新する。
