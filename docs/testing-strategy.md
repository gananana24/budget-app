# テスト戦略

更新日: 2026-09-26

この文書は、[プログラミング思想](./programming-philosophy.md) に基づく自動テストの判断基準と記述規則を定める。Vladimir Khorikov著『単体テストの考え方／使い方』を主な基準とし、このリポジトリで実行可能な規則へ具体化する。

## テストの目的

- テストの主対象はドメインロジックとする。
- テストコードには、実装方法ではなく成立すべき振る舞いを表現する。
- テスト数やカバレッジ率ではなく、変更に対する継続的な信頼を得ることを目的にする。

良いテストは、次の4本の柱で評価する。

1. 退行に対する保護
2. リファクタリングへの耐性
3. 迅速なフィードバック
4. 保守のしやすさ

内部メソッドの呼び出し順やprivateな構造へ結合したテストは、リファクタリングへの耐性が低いため避ける。

## 古典派（デトロイト学派）

- 一つの振る舞いを実現するコードのまとまりを「単体」とする。クラスや関数一つに限定しない。
- 単体テストは短時間で実行でき、他のテストから独立していることを求める。
- 協力オブジェクトを機械的にすべてモックへ置き換えない。
- 共有依存だけをテストダブルへ置き換える。
- 実装とのコミュニケーションではなく、出力や最終状態を検証する。

## テスト手法の優先順位

次の順に優先する。

1. 出力値ベースのテスト
2. 状態ベースのテスト
3. コミュニケーションベースのテスト

純粋関数の戻り値を確認するテストが最も望ましい。状態変化を持つ処理では、外部から観察できる最終状態を確認する。メソッド呼び出しの検証は、メール送信などアプリ外部へ出る副作用に限定する。

## AAAパターン

すべての自動テストは、原則としてArrange、Act、Assertの順に記述する。単体テスト、DB結合テスト、APIテストのすべてで、次のコメントを毎回明記する。

```ts
it("rejects an expense dated after today in Tokyo", () => {
	// Arrange
	const today = "2026-09-26"

	// Act
	const result = validateExpenseDate("2026-09-27", today)

	// Assert
	expect(result).toEqual({
		success: false,
		code: "OUT_OF_RANGE",
	})
})
```

- 3フェーズをこの順序で書き、空行で分ける。
- 前処理が不要でも、3つのコメントを省略しない。
- Actは原則一つにする。
- 同じ一つの振る舞いを確認する範囲では、Assertを複数書いてよい。
- ActとAssertを混在させない。
- 後始末はfixtureや `afterEach` へ分離し、主要なAAAの流れへ混ぜない。
- AAAコメントは、「コードコメントにはWhy notを書く」という原則の例外とする。

## テスト名

- テスト名は、前提と観察可能な振る舞いを英語の文章で表す。
- 関数名、メソッド名、内部の処理手順へ強く結合させない。
- 固定の命名テンプレートは強制しない。
- 失敗時に、何が壊れたかをテスト名だけで判断できるようにする。

## 単体テスト

- ドメインロジックの正常系、境界値、異常系を詳しく検証する。
- 現在時刻、乱数、DB、HTTPへ依存しない形で実行する。
- private関数や内部実装を直接テストしない。
- private処理を直接テストしたくなるほど複雑な場合は、独立したドメイン概念や純粋関数として分離できないか検討する。
- 単純な委譲、引数なしconstructor、一行のpropertyなど、固有の判断を持たないコードへ機械的にテストを追加しない。

## 結合テスト

自分たちが管理するアプリケーションとDBの接続は、実際のPostgreSQLを使って検証する。

- 生SQL、外部キー、一意制約、`CHECK`制約、トランザクション、冪等性を実DBで確認する。
- 主要な正常フローを、applicationからDBまで通して確認する。
- DB制約、認可、競合など、単体テストだけでは保証できない重要な失敗ケースを追加する。
- 同じ条件を単体テストと結合テストで無差別に重複させない。
- テストごとのデータを隔離し、実行順や前のテストが残した状態へ依存させない。

## 認可テスト

ブラウザ側のコードとリクエストは改変できる前提にする。読み取り、作成、更新、削除の各操作について、次を結合テストで確認する。

- 別利用者の家計IDやデータIDへ差し替えても操作できない。
- 他人の費目IDを指定して支出や予算を作成できない。
- 他人のIDと存在しないIDから、所属情報を区別できない。
- フロントエンドの非表示や `disabled` に依存せず、サーバー側で拒否する。

## テストダブル

### 実物を使う依存

- PostgreSQLはアプリケーションが管理する依存として扱い、結合テストでは実物を使う。
- RepositoryやStoreをすべてモックへ置き換えたテストだけで、DB連携の正しさを保証したことにしない。

### 置き換える依存

- Clerk、メール送信など、自分たちのテスト環境で状態を完全に制御できない外部サービスはAdapter境界で置き換える。
- 外部サービスとの実接続は、必要な環境で主要フローのスモークテストとして確認する。

### MockとStub

- Mockは、アプリ外部へ出る副作用を検証するために使う。
- Stubは、テスト対象へ入力を与えるために使う。
- Stubが何回呼ばれたかを検証しない。
- 内部クラス、Store、Repositoryの呼び出し順をテストの主張にしない。

## テストデータ

- 結果に影響する重要な値は、各テストのArrangeへ明示する。
- 検証対象ではない既定値だけをTest Data Builderやfactoryへ隠す。
- 共有された可変fixtureを使わない。
- 何を準備したか分からなくなる巨大な `beforeEach` を作らない。

## パラメータ化テスト

- 同じ振る舞いを異なる入力で確認するときに使う。
- 異なる理由で失敗するケースや、異なる振る舞いを一つの表へ詰め込まない。
- 各ケースがAAAとして読める構造を保つ。

## 再現性と独立性

- テストは実行順、現在時刻、乱数、外部ネットワーク、他テストのデータへ依存させない。
- 時刻や日付は入力として固定する。
- 外部ネットワークを通常の自動テストから呼ばない。
- flakyなテストを再実行で通す運用にせず、原因を修正する。

## カバレッジ

- コードカバレッジへ数値目標を設定しない。
- カバレッジは、テストされていない重要なコードを発見する補助指標として使う。
- ドメインロジックに未実行部分があれば理由を確認する。
- 数値を上げるためだけに、単純な委譲や防御コードのテストを追加しない。

## 避けるテスト

- privateな関数やフィールドを直接検証するテスト
- 内部メソッドの呼び出し順へ結合したテスト
- 実際の保存結果を確認せず、`save()` が呼ばれたことだけを確認するテスト
- 一つのテストで複数の異なる振る舞いを検証するテスト
- テスト同士で可変データを共有するテスト
- 本番コードと同じ計算をテスト側で再実装するテスト
- カバレッジ率を上げることだけを目的としたテスト
